# Refreshing dependency versions

`make update-deps` moves every dependency version this repository declares, in
one run. `make update-deps-dry-run` reports the same plan and writes nothing.

It's an action target like `proto`, not a gate. It needs the network and it
rewrites lock files, so it stays out of `CHECK_GATES` and out of everything
`make check` resolves. `make check` is offline and stays that way.

The logic lives in `scripts/update_deps.py`; the Makefile recipes are two lines
each.

## The four surfaces

| Surface | Found from | What a run does |
|---------|-----------|-----------------|
| Go modules | every language directory [`languages.txt`](./contracts/languages.txt) registers that carries a `go.mod` | `go get -u ./...` then `go mod tidy` |
| Python | every directory holding both a `pyproject.toml` and a `uv.lock`, which today means `python/` and `tools/techdocs-proof/` | `uv lock --upgrade`, raise each bare `>=` floor to the version uv locked, then `uv lock` again so the lock's requirement strings match |
| Tool versions | `scripts/*.sh`, the root Makefile, each registered language's Makefile, `buf.gen*.yaml`, and `.pre-commit-config.yaml` | report what floats, refuse the codegen pins, run `pre-commit autoupdate` |
| GitHub Actions | every `uses:` line under `.github/workflows/` | rewrite the sha and its trailing version comment together |

Nothing in that table is a path the script hard-codes except `tools/`, which is
the one directory the language registry cannot name because tool projects are
not language implementations. `make tools-typecheck` spells it the same way and
for the same reason. Add a third uv project and this target picks it up with no
edit; register a third language and its module and Makefile join the scan.

## The five dispositions

Every declared version gets one line in the report:

- `update`: this run moves it.
- `refuse`: protected by name in `scripts/update_deps.py`, with the reason
  printed beside it. See below.
- `hold`: declared in a shape this target does not rewrite, such as a
  requirement carrying an upper bound (`mcp>=2.0.0,<3.0`) or a `uses:` line
  naming a workflow in this repository. Renovate or a human handles those.
- `float`: no declared version at all. `scripts/ci-setup.sh` installs the Go
  tools at `@latest` on purpose (its own comment states the policy: local
  matches CI, always current), and it resolves uv, droast, betterleaks and
  trivy from whatever release is newest when it runs. There is no version token
  to move, so the report names them and moves on.
- `unknown`: a written-down version with no resolver here. This one fails the
  run. A new hand-pinned tool is either a deliberate pin, in which case it
  belongs in the protected table with its reason, or an accident, in which case
  it should float like the rest. Both answers are better than a silent skip.

A run whose discovery finds nothing fails rather than reporting a clean pass,
the same rule the hard gates follow (`scripts/_hardgate.py`).

## The gap this target cannot close

`go/Makefile` `install-tools` installs golangci-lint, gopls, gofumpt and
goimports with `@latest`, and `scripts/ci-setup.sh` does the same for CI. Those
four have no declared version anywhere, so neither this target nor Renovate can
move them. The binary on your PATH is whatever the last `install-tools` run
produced, and nothing records which run that was.

golangci-lint is where that bites, and it's the case that prompted this target.
Three places answer the question "which golangci-lint", and they disagree:

- `.pre-commit-config.yaml` pins `rev: v2.12.2`, so the commit hook runs that.
- `make check` runs whatever `install-tools` last put on PATH, which was 2.13.1.
- Renovate has 2.13.2 waiting in an open PR.

A commit fails the hook while `make check` passes, and nothing in the tree says
why. `make update-deps` closes the third gap by moving the pre-commit rev, and
it reports each `@latest` install as `float` so the remaining gap is at least
visible in the output rather than silent. Closing it properly means giving
those four tools a declared version, which changes the install policy
`ci-setup.sh` states, so it is a decision rather than a refresh.

## What it refuses, and why

**buf stays at v1.71.0.** `make proto` regenerates the whole tool tree, and
every committed baseline in `docs/contracts/` was captured under that buf. A
bump would change generated bytes, so the diff would be the baselines moving
rather than the code. `update-deps` names buf, prints that reason, and leaves
it alone. The buf remote codegen plugins in `buf.gen.yaml` and
`buf.gen.protovalidate.yaml` are refused for the same reason.

Two Python floors are refused as well:

- `protobuf`: its floor tracks the buf python and pyi plugin tags. Move the two
  together or every `_pb2` import raises at runtime.
- `protovalidate`: pinned exactly, because the generated `buf/validate`
  messages come from that release.

Moving any of these is a deliberate change with its own regeneration and its
own review. It is not something a refresh command should do on the way past.

## Action pins keep Renovate's form

Renovate's `helpers:pinGitHubActionDigests` writes each action as a commit sha
with the tag it follows in a trailing comment:

```yaml
- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7
```

The comment is the tracked ref, not decoration. A bump rewrites both halves
together, and it keeps the granularity the comment is written with: a pin
following `v7` moves to the newest `v8`-shaped tag, never to `v8.1.2`. A pin
following `v46.2.0` moves to the newest three-part tag. Tags come from
`git ls-remote`, which costs no GitHub API quota, the same reason
`scripts/ci-setup.sh` reads the releases/latest redirect instead of the API.

The SLSA reusable workflows are the exception. They verify their own ref at run
time and fail when it is a digest, so they stay on version tags. That rule is
declared once, in `renovate.json`, and this target reads it from there rather
than restating it.

## Renovate covers the same ground

Renovate runs daily at 04:00 UTC. It manages gomod (including indirect deps),
pep621, github-actions with digest pinning, and pre-commit revs, and it
automerges non-major updates through a branch rather than a PR. So this target
and Renovate both write `go.mod`, both `uv.lock` files, and the workflow pins.

That overlap is on purpose, and it's why every rewrite here copies Renovate's
pin form exactly. Diff one against the other and you get the same shape, so a
human can tell at a glance whether a hand-run refresh and the bot agree.

When to reach for the make target instead of waiting for the bot:

- You want the whole tree current right now, before a release or a bisect.
- You want to read the plan first. `make update-deps-dry-run` prints every
  declared version and its disposition without touching the network.
- Renovate's PRs are open and you would rather resolve everything in one local
  change.

Running both is safe. Whichever lands second sees the first one's work already
in the file.

## What it never does

It never touches git. No staging, no commit, no branch, no push. The target
rewrites files and stops, so reviewing the diff and deciding what to keep stays
human work.

It also never moves the Go language version in `go.mod` or `requires-python` in
a `pyproject.toml`. Renovate has custom managers for both, and a
language-version move deserves its own change.

One thing to know before you read a Go diff: `go mod tidy` writes that
directive in full, so a `go 1.26` line comes back as `go 1.26.0`. Same version,
longer spelling, and Renovate's custom manager reads either form.

## Reading a dry run

```console
$ make update-deps-dry-run

go modules (1: 1 update)
  update  go/go.mod: every module requirement 22 direct, 61 indirect (go get -u ./... then go mod tidy)

tool versions (26: 18 float, 6 refuse, 2 update)
  refuse  scripts/ci-setup.sh: github.com/bufbuild/buf/cmd/buf v1.71.0 (codegen must stay byte-reproducible and every committed baseline was captured under this version)
  ...
```

The dry run makes no network call, so it can't name the version a bump would
land on. It names what it would touch, what each target declares now, and the
disposition it would get. That's enough to review the plan before anything
rewrites a lock file, and it works offline.
